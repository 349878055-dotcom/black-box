# 找人办事 · 整体设计（分步做）

> 原则：**一次只做一层**。现在不上 SQL、不上实名、不拆微服务。  
> 铁律：客户只面对**人**；skill 是人的手脚；对话绑的是人。

---

## 1. 先分清四样东西（别混）

| 东西 | 现在在哪 | 谁管 | 客户看不看 |
| --- | --- | --- | --- |
| **虾米账号** | `data/users.json` | 客户登录 | 自己的号 |
| **对话** | `data/conversations.json` | 客户聊天 | 聊天列表 |
| **技能（代码）** | `adapters/skills/<id>/` | 工作台产、云端消费 | 不直接看 id |
| **帮手（人）** | **还没有**，写死在 App HTML 里 | 本仓库新增 | ✨ 里看的就是这个 |

技能已经有了（glyy / tuniu / meituan_waimai / njpkzyy）。  
缺的只是：**一张「人」表，人下面挂哪些 skill**。

不要为「人」新建一套数据库引擎。沿用现有办法：`cloud_orchestrator/data/` 下一个 JSON 文件。

---

## 2. 推荐方案：三张皮，一个闸

```
客户 App
  ✨ 找人办事 ──GET──► 云端 /api/v1/persons     （只读名单）
  点「找 TA」──POST──► 云端 创建对话 + persona   （已经有了）
  说话     ──WS───► 云端 agent
                         │
                         ├─ 读会话 persona.person_id
                         ├─ 只允许此人 skills[] 里的 skill_run
                         └─ 真执行还是走手机通道（不变）
```

**闸只有一道**：这个对话绑了谁，就只能动谁名下的 skill。没绑人，就当普通虾米，先不跑 skill（或保持现状全开——第 2 步再锁）。

客户不实名。评价以后再说。上台的人若要认证，走工作台，不进客户 App。

---

## 3. 数据怎么管（先 JSON，够用）

现有：`users.json`、`conversations.json`。  
新增一个：`cloud_orchestrator/data/persons.json`。

一份人长这样（和现在 HTML 里的 PEOPLE 对齐）：

```json
{
  "zhou": {
    "id": "zhou",
    "name": "周姐",
    "tagline": "生活帮手：挂号、买票、点外卖都能问",
    "city": "南京",
    "tags": ["生活", "挂号", "出行", "外卖"],
    "skills": [
      { "id": "glyy", "label": "鼓楼医院挂号", "how": "问清楚再挂" },
      { "id": "tuniu", "label": "火车票代下单", "how": "查完代下单，你去付钱" },
      { "id": "meituan_waimai", "label": "美团外卖找店", "how": "送到美团自己点" }
    ],
    "experience": [
      { "title": "一件事一条技能", "note": "问清楚再动手。" }
    ],
    "rating": 4.8,
    "jobs": 512,
    "week": 66,
    "comments": [],
    "status": "on"
  }
}
```

规则：

- **skill.id 必须能在 registry 里找到**，找不到就不给这个人挂。
- `status: on` 才出现在 ✨ 里。下台改 `off`，不要删记录。
- `rating / jobs / week` 第 1 步先手填；真统计放到很后面。
- `comments` 先放在人记录里，不要单独一张评论表。
- 会话里只存引用，不复制整个人：

```json
{
  "person_id": "zhou",
  "person_name": "周姐",
  "skills": ["glyy", "tuniu", "meituan_waimai"],
  "source": "showcase"
}
```

这就是「数据库」。人少、改得慢，JSON 比 Postgres 合适。真要上 SQL，等人数过百、评价要检索时再迁，字段已经对得上。

**不要做的：**

- 不要把 skill 代码存进数据库  
- 不要客户实名表  
- 不要「技能商城」独立货架（技能不单独卖，跟人走）  
- 不要展示厅再开一套聊天（对话只有虾米那一套）

## 4. 和云端怎么接（接口尽量少）

| 接口 | 谁用 | 作用 |
| --- | --- | --- |
| `GET /api/v1/persons?q=&cat=&sort=` | ✨ 列表 | 搜事、分类、排行 |
| `GET /api/v1/persons/{id}` | ✨ 个人页 | 技能 + 习惯 + 评价 |
| `POST /api/v1/conversations` | 已经有 | body 带 `persona` |
| agent 里读 `persona.skills` | 对话 | 限制 skill_run |

评价接口（`POST .../comments`）放到第 3 步，第 1 步不做。

App 侧：展示厅不要再内嵌死数据，改为请求上面两个 GET。  
「找 TA 办事」继续走现在的 `showcase:hire` → 创建会话，**这段已经通了**。

## 4.1 就是店面（第 1 步只做这一层）

标准店面三件套，没有新花样：

| 店面 | 我们 |
| --- | --- |
| 货架上的商品 | 帮手（人） |
| 商品详情 | 这个人能办的事 |
| 下单 | 找 TA 办事（已经有，建对话） |
| 后台改货架 | 改 `persons.json`（以后才做工作台） |

客户端：**格子是空的，请求来了把字段填进去。** 云端不返回 HTML。

**列表** `GET /api/v1/persons?q=&cat=&sort=`

```json
{
  "ok": true,
  "persons": [
    {
      "id": "zhou",
      "name": "周姐",
      "initial": "周",
      "color": "linear-gradient(145deg,#b8f0d8,#3ecf8e)",
      "tagline": "生活帮手：挂号、买票、点外卖都能问",
      "city": "南京",
      "tags": ["生活", "挂号", "出行", "外卖"],
      "skills": [
        { "id": "glyy", "label": "鼓楼医院挂号" },
        { "id": "tuniu", "label": "火车票代下单" }
      ],
      "rating": 4.8,
      "jobs": 512,
      "week": 66,
      "comments_n": 3
    }
  ]
}
```

格子对照：`name`→标题，`tagline`→一句介绍，`rating/jobs`→评分和单量，`skills[].label`→技能芯片，「找 TA」只带走 `id / name / skills[].id`。

**详情** `GET /api/v1/persons/zhou` 多返回 `greeting`、`skills[].how`、`experience`、`comments`。

未登录也可以逛店（只读）。登录只在点「找 TA」时需要。

## 5. 分五步，每步都能单独验收

### 第 0 步（已完成）

- ✨ 入口、找人 UI、去掉客户实名  
- 「找 TA」能建会话并带上 `persona`  
验收：手机上能逛、能点人。数据还是假的。

### 第 1 步 · 人从云端读（建议下一步就做这个）

只干三件事：

1. 新增 `store/persons.py` + `data/persons.json`（把现在 4 个人搬过去）  
2. 两个只读接口：列表、详情  
3. App 展示厅 `fetch` 云端，失败再退回本地兜底  

验收：改云端 JSON 里周姐的一句话，重开 ✨ 就能看见。还不用改 agent。

### 第 2 步 · 对话闸门

agent 里：

- 会话有 `persona.person_id` → `skill_run` 只允许 `persona.skills[]`  
- 没有绑人 → 先保持现在「虾米全能」**或**明确拒绝（你拍板；建议先保持全能，避免普通聊天被卡死）  

验收：找周姐说话，不能去调她没有的 skill。

### 第 3 步 · 评价

- 该会话里真正办过一件事（有一次成功的 skill_run）才能评  
- 评论追加进 `persons.json` 那个人的 `comments`  
- 客户不用实名，署名用虾米昵称  

验收：办完挂号能写下「问得很清楚」。

### 第 4 步 · 排行用真数

- 每次办成 +1 `jobs`，按星重算 `rating`  
- 本周单量用时间戳筛  

验收：综合 / 本周 / 好评三个排序不再手填。

### 第 5 步 · 以后再说（现在禁止开工）

- 工作台发布「人」而不是手改 JSON  
- 上台的人实名（工作台侧）  
- Postgres / 独立评论表  
- 客户侧技能货架、技能打分

## 6. 和现有工程怎么分工

| 仓库 / 端 | 只做这个 | 不做那个 |
| --- | --- | --- |
| **工作台 4.0** | 产 skill 文件夹 | 不管客户 UI、不管人设排行 |
| **个人助理5 云端** | 注册 skill；管 `persons.json`；对话闸门 | 不存客户平台登录态 |
| **虾米 App** | 展示人、创建绑人的对话、手机执行 skill | 不自己维护一份人名单当真相 |

登录医院 / 途牛：还是「我的 → 授权中心 → 内置浏览器」，和找人无关。

## 7. 建议你怎么拍板（做第 1 步之前）

只需要定两句话：

1. **普通聊天要不要还能跑全部 skill？**  
   建议：要。只有从 ✨ 选了人的那条对话才锁 skill。  
2. **人名单谁改？**  
   第 1～4 步：你改 `persons.json` 我帮你接接口。工作台发布人放到第 5 步。

拍板后从 **第 1 步** 开始，一次只交「云端人名单 + App 去读」，不做闸门、不做评价。
