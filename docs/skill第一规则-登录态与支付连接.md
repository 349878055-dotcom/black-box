# Skill 开发第一规则：登录态 + 支付连接（帽子理论）

> **做任何 skill，第一步必须先排查清楚这两件事**：
> **① 登录态**（怎么登录） **② 支付连接**（怎么支付，拿不拿得到）
> 这两件事都由"**帽子**"（请求时的环境身份/通道）决定。

---

## 一、核心结论（帽子理论）

**每个 skill 就两个关键东西：**

```
① 登录态 —— 怎么登录
② 最后的支付连接 —— 怎么支付（拿不拿得到）
```

**"帽子"（环境身份）决定这两件事：**
- 帽子不同 → **登录方式不同**（H5 cookie / 微信授权 / Bearer token）
- 帽子不同 → **拿到的支付连接可能不同**，**有的帽子根本拿不到支付连接**

**关键死结**：帽子（UA 伪装）能拿到"权限"（如下单），但**支付要"真 SDK/真环境"**（如微信 JSAPI 要真微信 SDK），帽子替代不了。

---

## 二、4 个 skill 验证表（实测）

| Skill | 帽子（环境） | 登录方式 | 能否拿到支付连接 |
|---|---|---|---|
| **tuniu（途牛）** | **H5 帽子** | H5/M网页 cookie | ✅ 拿到 `alipays://`（拉起支付宝 App） |
| **meituan（美团）** | **H5 帽子** | H5 cookie（手机号+验证码） | ❌ **拿不到**（submit 403，连支付链接都没有） |
| **meituan（美团）** | **微信帽子（真微信）** | 微信授权 | ✅ 能拿到（weapp 通道），但要真微信 SDK |
| **glyy（鼓楼医院）** | **接口 token** | 浏览器真人登录（Bearer+refresh 续期） | 接口内处理 |
| **njpkzyy（皮肤科）** | **微信帽子** | 微信小程序授权 | 微信支付 |

**关键印证**：同一个美团，**H5 帽子拿不到支付连接，微信帽子能拿到** → 证明"帽子决定能不能拿支付连接"。

---

## 三、帽子类型（环境身份）

| 帽子 | 登录态 | 典型权限 | 支付连接 |
|---|---|---|---|
| **H5 帽子** | H5 cookie | 看店/菜单/加购/结算（查询级） | 看平台：支付宝 scheme 可拉；微信 JSAPI 拿不到 |
| **微信帽子** | 微信授权/小程序态 | 下单（交易级，支付除外） | weapp 通道能拿，但支付要真微信 SDK |
| **App 帽子** | App token/uuid | 直接调 App API | 需 mtgsig 签名 |
| **接口 token** | Bearer token | 纯接口 | 接口内处理 |

---

## 四、规则落地（做 skill 第一步排查）

**新 skill 开发第一步，先排查填这张表：**

```
① 帽子：这个 skill 用哪个帽子进去（H5 / 微信 / App / token）？
② 登录态：这个帽子下怎么登录（cookie / 授权 / token）？存哪、怎么续期？
③ 支付连接：这个帽子下能不能拿到支付连接？
   - 能 → 什么格式（alipays:// 可拉起 / JSAPI 要真微信 / H5 收银台）？
   - 不能 → 换帽子（如微信帽子）能不能拿到？
④ 支付触发：拿到的支付连接，虾米能不能拉起？
   - alipays://（支付宝）→ 普通环境可拉 ✅
   - wx.requestPayment（微信 JSAPI）→ 必须真微信，虾米拉不起 ❌
```

**核心原则**：
1. **先确认"帽子"能拿到支付连接**，再谈下单自动化；拿不到就别承诺"自动支付"
2. **支付是独立一环**：帽子/UA 能解决到"下单"，支付要真 SDK/真环境
3. 每个 skill 文档都必须写清：帽子 + 登录态 + 支付连接格式

---

## 五、一句话

**做 skill 先查清楚：用什么帽子登录、这个帽子能不能拿到支付连接、虾米能不能拉起支付。** 这三件事是第一优先，排查不清后面全白做。
