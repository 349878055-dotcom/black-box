# 四方向审核思路（准备开审）

> 给谁看：开审前的共同尺子。  
> 审什么：手机 App、云端编排、Skill、接口约定 四层边界。  
> 不审什么：上一轮体检已修过的语法/导入/死代码；skill 制作方法论（那是工作台的事）。

---

## 0. 系统一句话

系统不是三个独立模块再加一堆 skill，而是：

**手机只执行，云端只编排，Skill 只声明+组蓝图，接口把这三层钉死。**

```
客户说话
  → 云端 Agent 按契约点菜（read_skill / skill_run / ask_user / login / 支付交付）
  → Skill 组 JSON 蓝图（不直连平台）
  → 手机补凭据、签名、真实 IP 打平台
  → 统一餐盒 {ok, data, error, need_login} 回云端
```

红线：

- 证件和平台登录只留手机，不上云
- 云端不直连平台（一切请求走手机通道）
- 不代付；交付只有 `query` / `action` / `pay_url` / `scheme`
- App 不认识 glyy / 途牛 / 美团 / 浦口

Skill 本身可以后期用接口约束。这次审的重点是：**四层边界有没有被代码或文档捅破。**

建议开审顺序：**接口 → 云端编排 → 手机 App → Skill**（先钉尺子，再量三边）。

## 共用纪律

- **确定错误** → 记下文件:行号，点头后再改。
- **边界 / 产品选择** → 待定，不擅自改。
- **文档与代码冲突** → 先记冲突，再定「改文档还是改代码」。
- 上一轮已修过的（确认误判、时段展平、ask_done 等）不重复翻案，只查有没有回潮。
- 结果仍写入：[`体检报告-确定项.md`](体检报告-确定项.md) / [`体检报告-待定项.md`](体检报告-待定项.md)。

## 方向 1 · 接口约定（尺子）

**这一层是什么：** 三层之间认哪几张表。  
**不是什么：** 某个医院接口好不好用。

### 必审 5 问

1. 蓝图字段（`request` / `credential` / `store` / `sign_*` / 占位符）App 与云端是否同一套。
2. 餐盒是否真的只有 `ok / data / error / need_login`；引擎有没有另认私货字段。
3. 枚举是否封闭（`deliver` 四种、`login` 两路、`transport=phone_only`、`sign_type`）。表外能力有没有偷偷加。
4. 文档三套是否打架：`plans/contract-v2-接口说明.md`、`plans/contract-v2-内部实现.md`、`app/src/core/README.txt`。
5. 升版闸门：缺能力是「改 skill」还是「改 App/大脑」。有没有人已经改了引擎来迁就某个 skill。

### 已知漏缝（开审时对准）

- 接口写单个 `contract.json`，代码已拆成 `meta.json` / `methods.json` / `login.json` / `payment.json`。→ **待定 27 已闭环**
- 内部实现仍写着已废弃的 `cloud` / `phone_fallback_cloud`。→ **待定 26 已闭环**
- `form` 字段表、图形验证码「看不清换一张」循环。→ **待定 33 已闭环**

### 判定

| 现象 | 判定 |
|---|---|
| 接口说了但引擎/App 不消费 | 空声明 |
| 代码做了但接口没写 | 私货 |
| 出现 `if skill == "tuniu"` 这类特判 | 接口失败 |

### 先看

- `plans/contract-v2-接口说明.md`
- `plans/contract-v2-内部实现.md`
- `app/src/core/README.txt`
- `cloud/cloud_orchestrator/channel/bridge.py`
- `app/src/core/java/com/xiami/host/SkillExecutor.java`（蓝图入口）

### 不审

四个平台的业务对不对（那是方向 4）。

## 方向 2 · 云端编排（大脑）

**这一层是什么：** 理解用户 → 按契约点菜 → 补参 / 登录 / 确认 / 交付。  
**不是什么：** 组请求头、算签名、直连平台。

### 必审 5 问

1. 工具循环是否干净：Hired 才 `skill_run`；先 `read_skill` 再跑；`customer_input` 缺参只走 `ask_user`；`confirm` 真拦；`requires` 自动补且匹配失败不取第一条。
2. 登录是否通用：只认契约 `login`（`sms_verify` / `browser`），无平台硬编码；`need_login` 只重试当前步；登录态不落云端。
3. 支付是否「data 里有 `pay_url` / `scheme` 就弹出 + 留链接」，不按 skill 名拦截；不代付。
4. 人设闸门：未雇人不能办事；雇了人只能跑名下 skill；检索 / 经验书是否真约束行为。
5. 禁降级：检索失败、手机不在线、解析失败，是直接报错还是 fallback。

### 已知漏缝（开审时对准）

- `README.md` 仍写「模型不可用回退 skill_list」，代码写绝不降级。→ 待定 28（文档回潮）
- 数据定稿要求删云端 `User.profile` → **已闭环**（users / MeUpdate / GET /me 均无 profile）
- 会话 `persona` 定稿要只挂上台卡 id → **已闭环**（`_clean_persona` 只留三字段）

### 判定

| 现象 | 判定 |
|---|---|
| 编排层出现平台 URL、签名算法、token 落盘 | 越界 |
| `if skill ==` 特判 | 不合格 |
| 失败被兜底成「好像成功了」 | 违背禁降级 |

### 先看

- `cloud/cloud_orchestrator/core/agent.py`
- `cloud/cloud_orchestrator/core/graph_engine.py`
- `cloud/cloud_orchestrator/core/login_flow.py`
- `cloud/cloud_orchestrator/core/master.py`
- `cloud/cloud_orchestrator/adapters/registry.py`
- `cloud/cloud_orchestrator/api/routes.py`
- `cloud/cloud_orchestrator/channel/ws.py`

### 不审

App 怎么画界面；某个 `api.py` 请求头对不对。

## 方向 3 · 手机 App（执行器）

**这一层是什么：** 纯执行器。只执行云端传来的指令 / 蓝图，不认识任何平台。  
**不是什么：** 选方法、触发登录、判断 glyy 是什么。

### 必审 5 问

1. 红线：不编排、不认平台、不跑 skill 代码、不把凭据回传云端。
2. 能力是否够接口用：占位符、签名枚举、凭据 `store`、browser 原语、sms 图回传、`open_external`、multipart、响应 `pick`。缺了是接口要砍，还是 App 要补。
3. 敏感数据：Keystore 加密、按邮箱隔离、资料卡不上云、日志脱敏。对照 [`数据格式设计-三句话定稿.md`](../archive/实现/数据格式设计-三句话定稿.md)。
4. 通道：WS 指令集（`skill_request` / `ask_user` / `ask_done` / 浏览器 cmd）与云端是否一一对应；断线、超时、等待态残留。
5. UI 是否掺了执行：`ui.html` 的 fetch 降级、内置浏览器登录 / 导出，是否会把凭据带进网页 JS。

### 已知漏缝（开审时对准）

- 定稿文档里的 Java 路径仍写旧的 `app/app/src/...`，实际已迁到 `app/src/core/java/...`。
- 上一轮：JS fetch 降级判定为「仅预览、生产走原生」，开审只查有没有回潮到真机路径。
- 本机若无 Android SDK，编译级只记「待真机验证」，不做假结论。

### 判定

| 现象 | 判定 |
|---|---|
| Java 里出现 glyy / tuniu 字符串业务逻辑 | 越界 |
| 接口有某签名 / 占位符、App 无 | 接口超前或 App 缺口 |
| 凭据或证件离开本机 | 违背三句话定稿 |

### 先看

- `app/src/core/java/com/xiami/host/SkillExecutor.java`
- `app/src/core/java/com/xiami/host/MainActivity.java`
- `app/src/core/java/com/xiami/host/CredentialStore.java`
- `app/src/ui/assets/ui.html`
- `cloud/cloud_orchestrator/channel/ws.py`

### 不审

皮肤好不好看；Gradle 工程壳怎么摆。

## 方向 4 · Skill（四个包，用接口去量）

**这一层是什么：** 挂在某人档案下的完整才艺包（契约 + 组蓝图 + 解析成餐盒）。  
**不是什么：** 把四个平台做成完美业务；也不是这次要把每个接口抠到字段级。

现有四个：`glyy` / `tuniu` / `njpkzyy` / `meituan_waimai`。  
原则：**后期用接口标准约束新 skill；这次只量「现有包能不能被接口收住、接口够不够收」。**

### 每个 skill 只过同一张表

1. 路径定性对不对：A 全自动 / B 送到确认页 / C 只给链接。支付拿不拿得到、登录走哪一路，跟 [`skill第一规则-登录态与支付连接.md`](../archive/写skill/skill第一规则-登录态与支付连接.md) 一致。
2. 契约拆分四件套（`meta` / `methods` / `login` / `payment`）能否被 registry 拼回接口要的那张表。
3. `methods[].name` ↔ `api` 函数；统一返回四字段；`need_login` 与是否带凭据一致；`deliver` 与是否真返回 `pay_url` / `scheme` 一致。
4. 有没有云端直连、`verify=False`、取列表第一条、查询却带 token。
5. 登录 / 支付声明是否客户手机真能走通（禁止把微信授权当交付路径）。

### 已知漏缝（开审时对准）

- tuniu 云端直发 + `verify=False` + 解析失败误报未登录（待定 13）→ 并入待定 26 / 28
- 查询不带登录态、操作才带 → **glyy 未回潮**（查询仍 `bearer=False`）

### 判定

| 现象 | 判定 |
|---|---|
| 违规能被接口规则一眼判出来 | 接口够用，记 skill 违规 |
| 必须打开 `api.py` 才能发现 | 接口缺字段 → 记回方向 1 补尺子，不在 skill 里打补丁 |

### 先看

各包：

```
store/archive_center/skill_archive/<人>/skills/<id>/
  contract/{meta,methods,login,payment}.json
  register.py
  api/_base.py
```

### 不审

接口没写死的平台细节（某个医院字段名）；skill 怎么从微信缓存挖出来。
