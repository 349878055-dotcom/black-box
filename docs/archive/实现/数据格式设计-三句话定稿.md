# 虾米数据格式设计（三句话定稿）

> 用途：给你研究「数据到底怎么存、怎么流动」。这份文档只定格式，**不改代码**。
> 三句话，先把边界钉死，再看每份文件装什么、不装什么，最后列出现在的漏缝。

---

## 0. 三句话总纲

1. **云端一个仓库、两个分区** —— 云端仓库 `data/` 里只有两个分区：客户资料区（`users.json` + `conversations.json`）和才艺分区（`cards.json`）。
2. **证件和平台登录只留手机** —— 真名、证件号、就诊人、乘车人、紧急联系人、医院 token、途牛 cookie，一律只放手机，不上云。
3. **skill 挂在个人档案里** —— 完整 skill（`contract.json` + `api/`）在 `skill_archive/<人>/skills/<id>/`；上台卡 `card.json` 只写挂载说明，不把源码塞进会话资料。

---

## 0.5 一般 App 是怎么做的？（淘宝 / 豆包，先看懂这个）

所有 App 都分成「两半」：**手机上的 App** 和 **云端的服务器**。

- **手机 App**：你看到的界面、你点的地方。它只存「这台手机上才用得到」的东西。
- **云端服务器**：账号、内容、所有用户共用的东西。它保证「不管你换哪台手机，东西都还在」。

**拿两个 App 举例：**

**淘宝**
- 手机上：登录凭证（token）、购物车缓存、浏览记录、本地设置。
- 云端：账号、商品、店铺、订单、评价、收货地址（云端，因为换手机、多设备、卖家发货都要用）。
- 关键：钱和交易都在云端，但**你付钱的那一下**（支付密码 / 指纹）只在手机上完成。

**豆包（AI 对话）**
- 手机上：登录 token、主题设置、本地缓存。
- 云端：账号、聊天记录、对话历史（云端，因为换手机还要看到之前的聊天）。

**为什么淘宝 / 豆包敢把敏感东西放云端？**
因为云端是**他们自己的服务器**，你信任他们，而且他们需要「手机 A 加购物车，手机 B 能看到」这种多设备一致。

**你的虾米为什么反而「证件和登录只留手机」？**
因为你的云端不是「你自己的」——云端跑的是第三方 agent 代码，替你去挂号、买票。你不信任它持有你的证件和平台登录态，所以分得比一般 App 更严：

- 需要「换设备也要在」的东西（账号、会话、上台卡）→ 照豆包，放云端。
- 只有「这台手机挂号 / 买票时要用」、又敏感的东西（证件、token）→ 只放手机。

**一句话判断标准（一般 App 都这么分）：**
> 换手机还要在的 → 云端；只在这台手机上用、又敏感的 → 手机。

**对照你的三句话：**
- 云端一个仓库两个分区（账号 + 会话 + 上台卡，换设备要在）✓
- 证件和登录只留手机（敏感 + 单机用）✓
- 才艺代码是能力不是资料（代码是程序，不是数据）✓

其实你已经在用一般 App 的做法，只是对「云端能存什么」比淘宝豆包更保守——因为你信任的不是自己的服务器。

## 1. 一图看懂（先看这张）

```
云端仓库  data/
├── 客户资料区   users.json + conversations.json   ← 号、聊天
└── 才艺分区     cards.json                         ← 上台卡、挂哪些 skill id

手机
├── 办事资料   真名 / 证件 / 就诊人 / 乘车人 / 紧急联系人   ← 不上云
├── 授权       鼓楼医院 token / 途牛 cookie                ← 不上云
├── 皮肤       主题 / 壁纸
└── 登录凭证    access / refresh token（云端只登记 refresh 能否吊销）
```

**两边怎么挂钩：**
- 客户资料区的 `user_id` 是**主键**（唯一、不变）。
- 才艺分区用 `owner_id` 指回这个 `user_id`（样品卡 `owner_id` 为空）。
- 字段**不合并**：证件、登录态永远不会因为挂钩而混进云端。

## 2. 云端 · 客户资料区

### 2.1 `users.json`（账号，一个人一条）

| 字段 | 存什么 | 别人能不能看 |
|---|---|---|
| `user_id` | 号的主键（UUID，不变） | 不能 |
| `email` | 登录名 | 不能 |
| `password_hash` | 密码哈希（pbkdf2），**明文永远不存** | 不能 |
| `nickname` | 虾米昵称 | 自己看 |
| `bio` | 一句话简介 | 自己看 |
| `status` | 账号开/关（active / disabled） | 不能 |
| `created_at` | 注册时间 | 不能 |

**不进这一区：** 真名、证件号、手机号、地址、紧急联系人、医院/途牛密码。
（现在代码里还多一个 `avatar`，属于展示字段，可留可去，不敏感。）

> ⚠️ **漏缝 1**：现在代码里 `User` 还带 `profile` 字段（见 [`users.py`](cloud/cloud_orchestrator/store/users.py:56)），这就是「办事资料」在云端的残留。定稿后**删掉**。

### 2.2 `conversations.json`（会话，一场对话一条）

| 字段 | 存什么 |
|---|---|
| `conversation_id` | 这场对话的 id |
| `user_id` | 属于哪个号 |
| `title` | 对话名 |
| `persona` | 跟哪张上台卡聊：`person_id` / `person_name` / `skills[]`（**只挂 id**） |
| `messages` | 聊天记录 |
| `pinned` | 是否置顶 |

**`persona` 铁律：** 只引用上台卡 id，**不把整张卡、更不把证件复制进来**。
（现状代码里 `persona` 是自由 dict `{nickname,prompt,bio}`，见 [`conversations.py`](cloud/cloud_orchestrator/store/conversations.py:26)。定稿目标是收敛成「引用上台卡」的结构。）

**不进这一区：** 同上黑名单。会话里即使聊到了证件号，也不落云端（清洗/不入库属后续工程，格式上先钉死「不收」）。

## 3. 云端 · 才艺分区

### 3.1 `cards.json`（上台卡，一张卡一个 id）

| 字段 | 存什么 |
|---|---|
| `id` | 卡号（当前样品：`zhang` / `lin` / `liu` / `ning`） |
| `owner_id` | 绑哪个虾米号（指回 `user_id`）；样品为空 |
| `status` | `on` 上场 / `off` 下场 |
| `name` | 台上怎么称呼 |
| `tagline` | 一句话 |
| `city` | 城市 |
| `tags` | 分类：挂号 / 出行 / 外卖 |
| `greeting` | 开场白 |
| `skills` | 挂上的才艺：`id` + `label` + `how`（**只有 id，没有 Python**） |
| `experience` | TA 怎么做 |
| `rating` / `jobs` / `week` | 评分、单量（以后系统算） |
| `comments` | 评价列表 |

**不进这一区：** 证件号、真名、办事资料、医院 token、才艺源代码。

> ⚠️ **容易混的两套 id**（专门标给你看）：
> - **卡 id**：`zhang` / `lin` / `liu` / `ning`（这张「人」的卡）。
> - **skill id**：`glyy` / `tuniu` / `njpkzyy` / `meituan_waimai`（挂在 `skill_archive/<人>/skills/` 下的文件夹名）。
> - 一张卡通过 `skills[].id` 挂一个 skill id：张医生→`glyy`，小林→`tuniu`，刘姐→`njpkzyy`，阿宁→`meituan_waimai`。
> - 你上面写的「张医生→glyy」指的是「卡挂的才艺」，不是卡号本身。两份 id 别当成同一个。

**才艺代码在哪：** `skill_archive/<人>/skills/<id>/`（如张医生的 `zhang/skills/glyy/`）。完整 skill 挂在个人档案下；上台卡只写挂载的 `id`，会话资料里不塞源码。

## 4. 只放手机、不放云端

| 放哪 | 是什么 | 现在在哪 |
|---|---|---|
| **办事资料** | 真名、证件号、就诊人、乘车人、紧急联系人 | 手机 `localStorage`（`xiami_profile_<邮箱>`） |
| **授权** | 鼓楼医院 token、途牛 cookie | 手机凭据库，不外传 |
| **皮肤** | 主题、壁纸 | 手机 localStorage |
| **登录凭证副本** | access / refresh token | 手机里持有；云端只登记 refresh 能否吊销 |

**办事资料的作用：** 挂号 / 买票时**本机带入**，云端 agent 不存这份。云端只收「这个号要办什么」，不碰「你是谁、证件几号」。

> ✅ **边界确认（你这次问的）：** 除了上面这四样，**其他全在云端**。
> 客户行为数据——**点过哪个新话题、收藏了什么、最近看过什么、逛了哪张上台卡**——都是云端的事
> （换手机还要在，且云端 agent 要据此个性化回复）。手机只是个「执行 + 本地敏感资料」的壳，
> **不存行为记录**。上表是「仅有的例外」，其余一律默认云端。

## 4.5 在代码里怎么分清楚（物理位置）

不用记概念，**看数据写进哪个文件就知道是哪一边**：

### 云端 = `cloud/cloud_orchestrator/data/` 目录下的 JSON 文件

| 云端文件 | 存什么 | 读写它的模块 |
|---|---|---|
| `data/users.json` | 号（账号） | [`users.py`](cloud/cloud_orchestrator/store/users.py:20) |
| `data/conversations.json` | 会话、聊天记录（话题在这） | [`conversations.py`](cloud/cloud_orchestrator/store/conversations.py:17) |
| `data/cards.json` | 上台卡 | [`cards.py`](cloud/cloud_orchestrator/store/cards.py:18) |
| `data/refresh_tokens.json` | 云端只登记「refresh 能否吊销」 | [`refresh_tokens.py`](cloud/cloud_orchestrator/store/refresh_tokens.py:16) |

### 手机 = App 里的两处本地存储

| 手机存储 | 存什么 | 在哪个代码 |
|---|---|---|
| 手机凭据库（SharedPreferences `xiami_creds`） | 医院 token、途牛 cookie（授权） | [`CredentialStore.java`](app/app/src/main/java/com/xiami/host/CredentialStore.java:21) |
| App 浏览器 localStorage | 登录凭证 `xiami_token`/`xiami_refresh`、办事资料 `xiami_profile_<邮箱>`、皮肤 `xiami_theme` | [`ui.html`](app/app/src/main/assets/ui.html:579) 一带 |

### 一眼判断法

- 数据文件在 `cloud/.../data/` → **云端**。
- 数据在 `CredentialStore` 或 `localStorage` 的 `xiami_*` key → **手机**。
- 现在云端 `data/` 里**没有任何证件/登录态文件**，手机里**没有任何会话/收藏/话题文件**——这就是分界，已经立住了。

## 7. 对照表（避免再混）

```
云端仓库
  客户资料区  users + conversations     ← 号、聊天
  才艺分区    cards                     ← 上台卡、挂哪些 skill id

手机
  办事资料    证件 / 就诊人              ← 不上云
  授权        医院 / 途牛登录态          ← 不上云
```

两边用同一个 `user_id` 挂钩：客户资料区是**主键**，才艺分区用 `owner_id` **指回来**。字段不合并。

## 8. 一句话问答（研究时兜底）

- **为什么证件不上云？** 办事资料只在挂号/买票时本机带入，云端 agent 只调度、不持有，出事面最小。
- **为什么 persona 只挂 id？** 会话只要知道「跟谁聊」；能力从该人 `skill_archive/<人>/skills/` 加载。复制整张卡或证件会造成重复存敏感数据。
- **skill id 和卡 id 一样吗？** 不一样。卡 id 是 `zhang/lin/liu/ning`，skill id 是 `glyy/tuniu/njpkzyy/meituan_waimai`，卡通过 `skills[].id` 挂 skill。
- **云端到底存不存 refresh token？** 不存副本，只登记「能否吊销」；真正的 token 在手机。
- **收藏、点过的话题、浏览记录放哪？** 放云端（客户行为数据，换手机还在、agent 要用来个性化）。手机只留「办事资料 + 登录凭证 + 皮肤」这四样，其余全在云端。

### B. 你特有的架构选择（别照搬一般 App，不用改）

| 选择 | 你的做法 | 为什么不能照搬一般 App |
|---|---|---|
| 存储用 JSON 文件 | `users.json` 等，无数据库 | 一般 App 用 MySQL/PostgreSQL 是为了成千上万用户并发；你是单用户自用，JSON 就是你的本地数据库，够用且好备份。不建议为对齐而上数据库。 |
| skill 执行 = 手机直连 | 云端组装蓝图 → 手机真实 IP 直连平台（`adapters/registry.py`、`app/.../SkillExecutor.java`） | 一般 App 是「服务器直调自己的 API」。你是「云端不持有平台登录态、手机持证直连」，这是为了「登录态留手机」这条铁律。手机直连就是你的对齐方式，不是偏差。 |
| `skills[].intents` | 卡里带意图词（`store/cards.py`） | 这不是敏感数据，是给本地检索用的索引词，保留。 |
| `avatar` | `User` 里预留的展示字段（`store/users.py`） | 一般 App 都有头像，非敏感，可留可去。 |
